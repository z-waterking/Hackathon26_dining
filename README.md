# 餐叙 · BJW 餐饮运营工作台

本地餐饮运营工作台，包含反馈中心、独立 Action 事项、六周菜单、菜品资料和消费分析。反馈 Excel 转换、回复、聚合事项审批、词云与规则排菜使用本地 SQLite；AI 回复草稿、全量反馈聚合、月报、排菜员及检验员通过服务端调用 Azure Responses API。运营人员编辑改善要求并审批，不查看或维护内部 Prompt。

项目目标与业务边界见 [项目文档](docs/项目文档.md)，原始笔记保留在 [project.md](project.md)。

## 启动

环境：Node.js 24、npm、PowerShell 7。首次在当前工作区运行：

从 GitHub 克隆后，需通过授权渠道另行取得菜库资料，并按原文件名放到项目根目录：`六周菜单.zip`、`新六周菜单.zip`、`第一轮+第二轮纯菜单库.xlsx`、`餐厅排菜规则+示例.xlsx`。已有运营历史可提供 `新餐厅反馈记录表-from 202607 2.xlsx`。**旧格式问卷在反馈中心直接上传，无须放到项目目录，文件名不固定。** 未提供目标工作簿时，转换使用内置十列格式。原始资料、反馈截图、解析产物、数据库及环境密钥不随代码提交；未取得菜库资料时，首次完整数据库初始化和依赖资料的测试不能运行。

```powershell
.\tools\Start-Dining.ps1
```

打开 <http://127.0.0.1:4317>。此命令在首次运行时解析菜库及已有运营历史、安装依赖，随后构建并启动。进入反馈中心上传旧格式问卷，系统自动转换入库。`Ctrl+C` 停止。当前机器已准备资料、依赖和数据库，未改前端时也可直接 `npm --prefix app start`。

若4317已占用，运行 `.\tools\Start-Dining.ps1 -Port 4318`，访问对应端口。服务只绑定本机地址。

前端开发：一个终端 `npm --prefix app start`，另一个终端 `npm --prefix app run dev`。Vite将`/api`代理到4317。生产试用只需要单服务启动。

## 本次新增工作流

1. **上传旧表 → 展示新表**：反馈中心点击“上传旧表 Excel”，选择 Forms 导出的旧格式 `.xlsx`（最多10MB，任意文件名）。系统按“我要”的表扬/建议/投诉/询问分支选取对应餐厅和正文，自动转为运营记录格式并入库。页面直接展示新表十列：反馈来源、序号、餐厅、日期、反馈内容、反馈跟进、反馈类别、问题分类、回复记录、备注；支持分页、展开长正文和进入反馈跟进。最近批次可重新查看、下载 XLSX/CSV。用户仅上传旧表，无需上传目标表。

   上传原件保存在 `app/data/uploads/` 的独立批次目录，转换结果保存在 `app/data/conversions/`。有目标模板时复用其列宽、历史回复及分类，没有时使用内置十列格式。重复上传不重复新增，也不覆盖已有人工回复和状态；新表页面展示最新跟进及回复，下载文件保留当次转换快照。
2. **总览与处理工作区**：反馈中心提供“反馈总览”和参考界面的三栏“处理工作区”。左栏筛选反馈队列，中栏核对原文、记录处理状态并起草/保存回复，右栏查看跨反馈热点和待审事项；完整台账及转换新表仍可查看。单条反馈的 AI 分析仅生成摘要与回复草稿，不再逐条生成 Action。
3. **独立 Action 事项**：在主导航进入“Action 事项”，默认汇总全部月份的真实单条反馈，也可选择月份。AI 将同类问题跨反馈归纳为 **0–6 个事项**，每项保留关联反馈及原文证据，不要求每条反馈都对应行动。超过1000条或150000字符时提示缩小范围，不静默截断。运营可调整标题、说明、目标档口、优先级、排菜调整要求及启用状态，并记录审批理由后批准或拒绝。新事项一律待审批；重算复用同主题事项并保留人工修改。
4. **月度汇总**：选择月份，打开“月度汇总”查看词云。字体大小对应提及该词的真实单条反馈数；月级汇总行、隔离试填和演示数据不混入计数。可生成 AI 月报；原文、回复、状态或内部分析配置变化会使旧摘要失效。
5. **六周排菜与影响记录**：菜单页启用 AI 排菜员与检验员，一次生成全部档口的六周工作日菜单。只有已批准且启用、有排菜调整要求的真实 Action 进入正式排菜。排菜员结合源规则输出候选偏好/减少/禁用策略，规则引擎实际选菜，检验员检查完整六周菜单及本地规则报告。人工换菜后重新检验；批准事项或排菜要求变化需重新生成。运行留痕展示规则与 Action 快照、决策、检验、相同种子下基线和本次选用次数、变化槽位及未落实原因，不展示内部 Prompt。

服务、清洁、排队等非排菜事项的排菜调整要求为空，不强行影响菜品选择。修改已批准事项的业务内容需要再次确认审批。原“运营调试”Prompt 编辑界面已撤下；内部配置由应用维护，运营通过 Action 的业务要求影响后续规划。

### 零 API 示例流程

在 Action 模块点击“加载示例 Action”，创建独立标记的 **12 条示例反馈、4 个聚合事项**，每项关联3条证据；重复加载不覆盖人工编辑或审批。选一项排菜示例，批准后进入六周菜单选择“模拟排菜测试”，生成模拟菜单并查看影响与检验。**加载示例 → 人工批准 → 模拟排菜/重新模拟检验**均在本地完成，不调用 Azure；点击真实 AI 聚合或 AI 排菜入口仍会使用 API。

模拟流程只执行内置的菜品偏好、减少、禁用映射，服务事项不改变菜单。若编辑示例的排菜要求、档口或优先级，原映射会失效，并显示未落实/需人工验证；模拟器不会理解任意新增自然语言要求。示例不计入真实反馈统计和正式排菜。

反馈回复不会自动发送邮件。AI 检验结果仍需人工审核；缺少标签、规则冲突或候选不足会保留问题。候选策略的增减记录并不等于每餐配比等所有自然语言要求已经满足，须结合检验报告确认。

## Azure AI 配置

服务端自动加载 `app/.env`（Git 忽略）。新机器复制 `app/.env.example` 为 `app/.env` 后填入密钥。本机已配置用户提供的 endpoint、部署 `gpt-5.6-sol` 与版本记录 `2026-07-09`；调用时 `model` 使用部署名称，版本在 Azure 端管理。密钥不会写入前端、响应或版本日志。

```dotenv
AZURE_OPENAI_RESPONSES_ENDPOINT=https://41626-me2j04fd-eastus2.services.ai.azure.com/openai/v1/responses
AZURE_OPENAI_DEPLOYMENT=gpt-5.6-sol
AZURE_OPENAI_MODEL_VERSION=2026-07-09
AZURE_OPENAI_API_KEY=填入密钥
AI_MONTHLY_BUDGET_USD=150
AI_INPUT_USD_PER_MILLION=
AI_OUTPUT_USD_PER_MILLION=
AI_TIMEOUT_MS=180000
```

150 USD 当前作为可配置预算参考。单价未确认时仅记录调用和 token 用量，不估造费用；填入实际每百万输入/输出 token 单价后显示估算费用，达到预算会拒绝新的调用。这不是 Azure 侧硬账单限制，进行中调用及其他应用的用量仍以 Azure 账单为准。不配置密钥时本地功能仍可运行，AI 入口会提示未配置。

## 转换与工作流接口

所有接口仅供本机访问；除文件上传外，写请求使用 `Content-Type: application/json`。上传使用 `application/octet-stream` 原始文件字节，`X-File-Name` 为经 `encodeURIComponent` 编码的文件名。

| 接口 | 用途 |
| --- | --- |
| `POST /api/feedback/upload` | 上传旧格式XLSX，自动转换、幂等入库；返回批次、映射与计数 |
| `GET /api/imports/:id/rows` | 返回转换后的十列表格及关联反馈ID，供系统直接展示 |
| `POST /api/feedback/convert`，`{"import":true}` | 兼容旧的本机固定文件接口；页面日常使用上传入口 |
| `GET /api/imports/:id/download?format=xlsx` | 下载该批次目标格式工作簿；也支持 `csv` |
| `POST /api/feedback/:id/analyze`，`{}` | 单条反馈摘要与回复草稿，不创建行动；相同输入复用分析 |
| `POST /api/feedback/:id/reply`，`{"text":"回复内容"}` | 保存本地回复及历史 |
| `GET /api/actions/summary?month=&demo=false` | 读取全部月份真实反馈的聚合摘要、来源数及相关事项；month 可选 `2026-09` |
| `POST /api/actions/summarize`，`{"month":"","demo":false,"force":false}` | 整批反馈聚合为0–6事项；缓存复用，保留人工编辑和审批 |
| `POST /api/demo/actions`，`{}` | 幂等加载12条演示反馈和4个聚合事项，不调用AI |
| `PATCH /api/actions/:id` | 编辑、批准或拒绝行动并记版本；状态 `pending/approved/rejected` |
| `GET /api/feedback/summary?month=2026-09` | 本地词云与月度统计 |
| `POST /api/feedback/summary`，`{"month":"2026-09"}` | 按需生成/复用 AI 月报 |
| `GET /api/settings`、`PUT /api/settings` | 已停用并返回404；不公开内部 Prompt/配置，运营使用 Action 模块 |
| `POST /api/plans/generate`，原参数加 `useAi:true` | 顺序运行排菜员、六周引擎、检验员 |
| `POST /api/plans/generate`，原参数加 `demo:true` | 仅使用已批准示例事项运行本地模拟排菜，不调用AI |
| `POST /api/plans/inspect`，完整菜单 | 人工换菜后重新检验 |
| `GET /api/menu-runs/:id` | 读取业务范围、规则/Action快照、决策、检验及影响证据；不返回内部 Prompt或原始模型输入 |
| `GET /api/ai/status`、`GET /api/audit` | 查看 AI 用量和最近业务变更日志 |

API 响应不回传 `rawPrompt`、角色 Prompt、内部配置和原始角色输入。模拟菜单重新检验也须显式带 `demo:true`，正式/模拟模式不能混用。开发修改记录见 [docs/CHANGELOG.md](docs/CHANGELOG.md)；各模块详细修改见 `docs/logs/`。运行中的回复、审批、转换及聚合分析另存 SQLite `audit` 表。

## 数据现状

- 当前本机解析17份工作簿、72张工作表、22,564个非空行（含保留的2.xlsx/3.xlsx两个模板版本）；历史反馈只取2.xlsx，避免重复导入模板。
- 初始2,733个档口售卖项，不等于2,733道全局唯一菜。名称、价格或档口不同不擅自合并。
- 保留1,416份配方证据和56个源表公式错误的定位。配方可能有重复版本，成本是原表缓存值，不是重新核算结果。
- 当前本地197条反馈记录，含月汇总和疑似重复：146条有效历史记录，加上问卷149条中转换的139条，其中88条与历史同来源ID且正文一致，合并来源后净新增51条。2026年5月ID 1–10沿用既有试填隔离规则，报告保留定位；48个渠道占位空行不入库。
- 历史跟进文字不等同完成证明，初始没有强行标为已完成的记录。
- 无真实POS明细。默认报表为空，演示交易仅在内存中，不写入真实数据库。
- Action示例另存12条明确标记的演示反馈与4项聚合事项，不改变上述真实反馈口径；与POS内存演示是独立功能。

解析目录为本机 [materials/inspection/inventory.json](materials/inspection/inventory.json) 及对应逐表JSON/TXT。菜单菜库初始化只执行一次；反馈问卷由用户上传触发转换，重启不会再次读取固定问卷或覆盖人工记录。重导同一记录补充来源，不覆盖人工回复、负责人和处理状态；同来源ID而正文变化时保留为待核验冲突。历史模板的新独立反馈和菜库增量更新仍需单独制定策略。

## CSV 约定

CSV使用UTF-8、逗号分隔、标准CSV引号规则。CSV单批最多10,000行，请求不超过5MB。反馈中心另支持上传原始Forms格式XLSX（10MB），自动转换为新表；其他任意版式Excel不作猜测映射。

### 反馈导入

```csv
content,restaurant,date,channel,type,category,threadId,owner
示例反馈请替换,寻味列车,2026-09-05,手工,建议,口味,,
```

`channel`：手工、口头、微信群、二维码、邮件；`type`：建议、投诉、表扬、询问。按规范化字段内容去重，重导同一行不新增，不覆盖现有处理状态。CSV记录默认未处理及疑似重复待核验。

邮件线程续写目前通过“录入反馈”入口使用相同渠道与线程标识完成；CSV不是邮箱连接器。模板里的示例不是实际反馈。

### POS 导入

页面可下载CSV模板。金额为人民币，时间为北京时间，不含时区后缀。

```csv
transactionId,lineId,time,stall,dishId,dishName,quantity,amount,status,unit
POS01-20260905-001,1,2026-09-05T12:30,寻味列车,,奥尔良鸡腿,2,16,sale,份
POS01-20260905-R01,1,2026-09-05T13:30,寻味列车,,奥尔良鸡腿,-1,-8,refund,份
```

- 唯一键为交易号+明细行号。交易号不是全局唯一时应加终端/门店前缀；退款使用自己的交易号，不覆盖原交易。
- `status`：`sale`、`refund`、`void`。销售数量为正；退款数量为负、金额非正；作废不计。金额最多两位小数。
- `unit`：份、个、斤、100g。不同单位不混排行，多件套餐以套餐份计，原规格保留在菜名/价格文字中。
- `dishId`可从菜品资料导出获取。留空时按“档口+完全一致菜名+单位”唯一匹配，多价版本或无法唯一匹配时保持未映射。
- 未映射明细仍计入收入，不进入菜品排行。只含刷卡金额时不能推断菜品销量，交易数不是人数。
- 同键同内容跳过，同键不同内容整批回滚。纠错需冲正记录或后续更正流程，不支持重导覆盖。
- 模板示例不是实际交易，正式导入前必须替换。

### 菜单生成与导出

点击“一次生成全部档口六周菜单”，一次请求覆盖当前菜库中全部17个档口分组、六周周一至周五和所选餐次。无需逐档口操作；缺少可用候选的档口仍保留待补菜位置。所选餐次统一应用于全部分组，实际开餐时间、早餐库归属及固定主食需要现场复核。

默认按周展示所有档口，可筛选某个档口、周次或餐次；这些筛选只影响查看。点击菜名查看辣度、素食性、热量、过敏原、标签依据、来源及配方证据，也可在明细中更换同档口菜品。换菜后整份重新校验，点击“保存整份草案”保存为一个完整版本。已有单档口历史草案继续可读，不会自动补成全部档口。

“导出六周菜单”输出周菜单表，列为：**周次、日期、餐次、档口、周一、周二、周三、周四、周五**。日期为对应周的起止日期，每个工作日单元格仅含菜名及原售价，空槽位标为“待补菜”。导出始终覆盖整份草案，不受当前筛选影响；不导出菜品ID、槽位、种子、状态、规则、原料、营养或来源明细。

纯菜单文件用于阅读、分发或打印，不是内部排菜备份；旧菜单明细CSV导入入口已撤下，调整在页面菜品明细中完成。

## 存储与安全

首次启动生成应用私有数据库`app/data/dining.sqlite`，不纳入Git。备份前停止服务并复制整个`app/data`目录；恢复时保持服务停止，恢复该目录后重启。不要删除数据库来刷新页面，这会丢失人工记录。

原始资料、解析产物、测试截图可能包含个人反馈和身份线索，不应公开上传。界面未展示身份专列，但正文仍可能含签名，不属于完整脱敏。当前没有SSO、角色隔离、加密备份或生产审计，不能直接开放网络访问。

真实邮箱/POS接口、跨档口全局求解、自动营养核算、采购库存及损耗预测尚未接入。AI已接入指定Azure endpoint，仅在用户选择AI流程时发送所需业务文本；源表身份专列不进入反馈分析请求，但正文仍可能含身份线索。上线门槛见项目文档。
