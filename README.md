# 餐叙 · BJW 餐饮运营工作台

本地餐饮运营工作台，包含反馈中心、独立 Action 事项、六周菜单、菜品资料和消费分析。反馈 Excel 转换、回复、聚合事项审批、词云与规则排菜使用本地 SQLite；AI 回复草稿、全量反馈聚合、月报、排菜员及检验员通过服务端调用 Azure Responses API。改善事项独立审批；左下角“Prompt 与规则”可查看和维护下一次生成使用的业务指令。

项目目标与业务边界见 [项目文档](docs/项目文档.md)，原始笔记保留在 [project.md](project.md)。

## 启动

环境：Node.js 24、npm、PowerShell 7。首次在当前工作区运行：

从 GitHub 克隆后，需通过授权渠道另行取得菜库资料，并按原文件名放到项目根目录：`六周菜单.zip`、`新六周菜单.zip`、`第一轮+第二轮纯菜单库.xlsx`、`餐厅排菜规则+示例.xlsx`。已有运营历史可提供 `新餐厅反馈记录表-from 202607 2.xlsx`。**旧格式问卷在反馈中心直接上传，无须放到项目目录，文件名不固定。** 未提供目标工作簿时，转换使用内置十列格式。原始资料、反馈截图、解析产物、数据库及环境密钥不随代码提交；未取得菜库资料时，首次完整数据库初始化和依赖资料的测试不能运行。

```powershell
.\tools\Start-Dining.ps1
```

打开 <http://127.0.0.1:4317>。此命令在首次建库时解析菜库及已有运营历史、安装依赖，并一次性导入原菜单，随后构建并启动。已有库启动不重新读取原菜单Excel。进入反馈中心上传旧格式问卷，系统自动转换入库。`Ctrl+C` 停止。当前机器已准备资料、依赖和正式入库菜品，未改前端时也可直接 `npm --prefix app start`。旧库若提示尚未入库，执行 `node tools/Import-StallCatalog.mjs --apply` 后启动。

主导航页面记录在地址栏（例如 `/#menus`）。反馈中心、Action事项、六周菜单、菜品资料、消费分析刷新后保留当前页面；支持直接链接及浏览器前进/后退，不同浏览器标签页互不覆盖。这里只记住当前页面，不自动保存未提交表单，也不在刷新时重新发起AI生成。

需要确认真实 AI 连通性时，在允许访问配置的 Azure endpoint 的终端运行 `.\tools\Start-Dining.ps1 -VerifyAi`（或 `npm --prefix app start -- --verify-ai`）。它会在同一个后端进程内发送一次不含业务数据的小型付费请求，打印模型和 token 数；默认启动不调用 AI。若提示 `EACCES/EPERM`，是本机出站权限拒绝，需要在获准联网的环境重启后端，不是刷新页面或换模型能解决；无需关闭防火墙或TLS验证。

若4317已占用，运行 `.\tools\Start-Dining.ps1 -Port 4318`，访问对应端口。`DINING_NETWORK` 默认是 `local`，仅监听本机；当前机器的 `app/.env` 已设为 `DINING_NETWORK=lan`。

公司内网访问可显式启动：

```powershell
.\tools\Start-Dining.ps1 -NetworkMode lan
```

同事打开 <http://10.2.165.12:4317>（本机当前内网 IPv4，地址变化后需相应更新）。`lan` 模式监听 `0.0.0.0`，页面与 `/api` 由同一服务提供；公司网络需要能互通，Windows 防火墙需允许该端口的入站访问。`-NetworkMode` 优先于 `app/.env`，使用 `-NetworkMode local` 可切回仅本机访问。

若防火墙阻止访问，在管理员 PowerShell 中运行 `.\tools\Enable-DiningLanFirewall.ps1 -Port 4317`，仅放行 Node 服务在当前私网 IPv4 和指定端口上接收私网来源连接。内网 IP 变化后需重启服务并重新运行此脚本。

前端开发：一个终端 `npm --prefix app start`，另一个终端 `npm --prefix app run dev`。Vite将`/api`代理到4317。生产试用只需要单服务启动。

### Cloudflare 临时演示

先保持应用在本机 4317 端口运行，再在另一个 PowerShell 中启动无需登录的 Cloudflare Quick Tunnel：

```powershell
.\tools\Start-DiningTunnel.ps1 -Authentication none
```

脚本在后台启动隧道并输出临时 HTTPS 地址。`none` 模式下，页面、API、上传和下载直接可访问，不生成或提示凭据；持有地址的人可以查看和操作项目。显式选择的模式保存在私有文件 `app/data/cloudflare/settings.json`，以后运行 `.\tools\Start-DiningTunnel.ps1` 会复用该模式。HTTPS、当前隧道的 Host/Origin 校验和上游 loopback 限制继续生效；本机 4319 端口的网关仅监听 loopback，不改变现有本机或内网访问配置。

若需恢复账号口令，先停止隧道，再运行 `.\tools\Start-DiningTunnel.ps1 -Authentication basic`。尚未保存模式时的通用初始默认值为 `basic`：账号为 `dining`，首次生成随机口令，后续复用 `credentials.json`，启动时提示 `app/data/cloudflare/access.txt` 凭据路径。两种模式切换均需先停止再启动；设置、凭据和 `cloudflared` 程序不纳入 Git。

结束演示时运行：

```powershell
.\tools\Stop-DiningTunnel.ps1
```

停止脚本只关闭隧道和网关，应用继续运行。电脑需保持开机、联网且不休眠。Quick Tunnel 无需 Cloudflare 账号或域名，但重启后地址会改变，且没有 SLA，适合短期演示。长时间 AI 排菜可能触发 Cloudflare 超时，必要时从原内网地址执行。固定域名和公司 SSO 需另行配置 Cloudflare 账号、域名及 Cloudflare Access。

## 本次新增工作流

1. **上传旧表 → 展示新表**：反馈中心页首点击“导入原始文件并转换”，在弹层选择 Forms 导出的旧格式 `.xlsx`（最多10MB，任意文件名）；台账内“上传旧表 Excel”也使用同一转换入口。系统按“我要”的表扬/建议/投诉/询问分支选取对应餐厅和正文，自动转为运营记录格式并入库。页面直接展示新表十列：反馈来源、序号、餐厅、日期、反馈内容、反馈跟进、反馈类别、问题分类、回复记录、备注；支持分页、展开长正文和进入反馈跟进。最近批次可重新查看、下载 XLSX/CSV。用户仅上传旧表，无需上传目标表。

   上传原件保存在 `app/data/uploads/` 的独立批次目录，转换结果保存在 `app/data/conversions/`。有目标模板时复用其列宽、历史回复及分类，没有时使用内置十列格式。重复上传不重复新增，也不覆盖已有人工回复和状态；新表页面展示最新跟进及回复，下载文件保留当次转换快照。
2. **反馈中心首页**：进入后直接显示首页，不再切换“处理工作区”或“反馈台账”页签。顶部 AI 横幅跳转独立 Action 事项；下方规整展示四个仪表卡：按反馈类型分类的趋势、反馈类型分布、外置词云、处理概览，随后是可筛选和处理的反馈台账。统计使用真实单条反馈，月份为空时覆盖全部月份；“投诉”和历史“批评”在图表中合并为“批评”，保留原始台账分类。完整台账、转换新表及单条反馈跟进仍可查看；单条 AI 分析仅生成摘要与回复草稿，不逐条生成 Action。聚合、编辑及审批事项统一在 Action 模块操作。
3. **独立 Action 事项**：在主导航进入“Action 事项”，点击 **AI 生成改善事项**，通过已配置的 Azure `gpt-5.6-sol` 分析全部月份真实单条反馈，也可选择月份。页面不提供示例入口，事项以响应式卡片展示：类型配色、优先级、措施摘要、原文依据、相关反馈数和审批状态；点击“查看与审批”打开详情，可读完整内容、编辑业务要求、批准/拒绝及查看历史。AI 将同类问题归纳为 **0–6 个事项**，按“核验、措施、验收”描述可实施的改进，不要求每条反馈都有行动。AI选择原文段落编号，服务端从完整原文快照回填证据，避免引用被改写。超过1000条或150000字符时提示缩小范围，不静默截断。新事项一律待审批；每次显式生成都会调用AI，重算复用同主题事项并保留人工修改，失败不会回退示例或覆盖既有事项。
4. **词云与月度汇总**：首页词云直接展示当前月份范围的高频餐饮主题，无需打开弹窗；字体大小对应提及该词的真实单条反馈数，同条重复提及不重复计数。词频由本地餐饮词表及现有菜名、档口匹配，不调用 AI；月级汇总行、隔离试填和演示数据不混入计数。单月“月度汇总”仍可按需生成 AI 月报；原文、回复、状态或内部分析配置变化会使旧摘要失效。
5. **真实 GPT 六周菜单**：菜单页默认启用 AI，从已正式入库的菜品和档口映射取候选，再逐周、逐档口分别调用 GPT 选择真实菜品，不在生成时读取原始菜单Excel。每档口只收到自己的完整候选、前面成功周次和本周已排其他档口的协调信息；一周全部档口完成即展示，六周完成后独立 GPT 检验。局部结构/引用或可修复硬规则问题最多追加两次当前档口纠错，不重排成功前缀，网络或上游失败不自动重试。审核后最前面显示客观质量分，冲突收在详情，批准 Action 的要求和实际落实菜品位置单独显示。源规则不可被 Action 覆盖，生成或80分以上不代表人工批准。生成动画只在菜单页，其他页面可继续使用。

服务、清洁、排队等非排菜事项的排菜调整要求为空，不强行影响菜品选择。修改已批准事项的业务内容需要再次确认审批。Action模块只编辑业务事项；独立的“Prompt 与规则”页编辑生成指令，不替代事项审批。

### 排菜规则与 Prompt 位置

- 规则源文件：根目录 `餐厅排菜规则+示例.xlsx`。启动和正式生成前读取当前文件并仅同步规则元数据，不重新导入反馈或覆盖菜品标签。当前为16条规则、4条固定主食和4条固定出品来源（宽窄巷子午晚餐各2条）；保存工作表/单元格来源和SHA256。
- 新生成的Prompt由 `app/server/prompt-config.mjs` 提供已保存业务文本，`prompt-builders.mjs` 统一组合：排菜角色指导 → 按档口逐条列明的启用规则 → 已批准Action应用方式与动态清单 → 程序硬约束及结构化输出协议。`direct-menu-planner.mjs` 复用同一构造函数，预览和真实Responses `instructions`一致；`menu-stall-planner.md`/`menu-planner.md` 仅供没有新配置快照的旧记录兼容。
- 检验指令与编排入口：`app/server/menu-workflow.mjs`。GPT 只选择真实菜库索引，服务端映射回原始ID并检查数量、价格、档口和引用，不自动替模型补菜。
- 老广老北/百变厨房规则要求人工上传，未提供时保留待补；一锅烟火若没有≥30元候选保留对应缺位。缺标签只提示待核验，不虚构已知值；缺专属规则的档口仅生成通用候选草案。固定主食沿用原文显示并加入CSV。
- 保存结果仍是待审核草案，不是自动批准或发布。显式关闭AI才使用本地规则草案；模拟菜单不调用真实GPT。

### 编辑 Prompt 与规则

左下角点击 **Prompt 与规则**（`/#prompts`），可维护四部分：反馈生成Action业务Prompt、全部AI排菜规则、排菜System业务Prompt、已批准Action注入Prompt。三段文本与规则统一“保存并生效”，不用重启，下一次反馈聚合/新菜单生成读取新版本。规则支持新增、删除、启停、档口编辑、搜索和分页；源Excel原文仍保留，运营修改独立入库，不会被启动同步覆盖。

页面可展开服务端的已保存完整Prompt。排菜页只保留一个“最终 Prompt 预览”，标明排菜指令、自动加入的规则、已批准 Action、输出格式与固定校验四部分，不再要求选择预览档口。预览是全部可参与 Action 的组合总览，真实调用仍按当前档口筛选事项；动态反馈、菜库索引、日期、已生成周次及输出schema运行时另附，不把预览伪装成过去某次请求。当前批准清单只读，具体事项内容与审批仍在Action页维护。未保存草稿不进入预览或模型。

**边界**：可编辑的是AI业务规则文本，不是任意程序逻辑。菜品归属、价位槽位、人工菜单/固定来源、本地重复与标签核验等程序约束单独只读列明；改写业务文本不会取消这些校验。检验员和定点修复的技术协议也不是此次三段编辑项。改动与本地硬约束冲突会继续被检验指出。

版本与来源指纹防止多个窗口互相覆盖；冲突返回409并保留未保存内容。已开始的生成使用启动时的Prompt/规则快照，不中途切换；完成或读取旧菜单时会提示与新配置不一致，旧菜单不自动改写，恢复/复检须匹配配置。反馈聚合缓存按真实Prompt指纹失效，下次按新要求分析，但不会覆盖已有人工审批。

当前部署没有单独的管理员身份/角色权限：能访问应用的人也能访问此配置页，包括已开放的内网/演示隧道。Prompt页只提供业务文本和规则，不返回API密钥、环境配置或原始模型响应；不要在Prompt中粘贴密钥等机密。

### 逐周生成、逐周展示

菜单页点击生成一次后自动完成六周，无需每周再点一次：**第 1 周各档分别生成并校验 → 展示完整第 1 周 → 每档把自己的全部成功周次输入 AI → 第 2 周各档分别生成并追加展示 → 依次完成第 6 周 → 独立检验员复核**。页面显示当前生成周次和 6 格进度，未生成周次不提前画成“待补菜”。

生成期间可以查看已完成周次、切换餐次/档口或去其他页面；不会阻塞整个系统。逐周预览为只读，六周和检验全部完成后才开放完整草案的编辑、保存与导出；不会自动批准。原先草案独立保留，中途失败不会把已完成周次清掉，也不会生成示例代替。

前后端使用同一 `diningApi` 的逐周进度流，不等待全部六周结束才返回。浏览器断开只停止接收，服务端继续已有任务并记录进度；重新进入后先查看“恢复生成记录”，避免重复付费生成。

### 失败后继续生成

菜单页点击 **恢复生成记录**，可查看最近真实生成的已完成周次和失败位置。点击 **继续生成剩余周次** 时，系统创建新运行记录，重新核验并复用原有成功周次，仅调用剩余周次和检验员；若六周已完成、仅检验失败，则只重跑检验。不修改原失败记录，也不自动保存或批准菜单。点击 **查看已生成菜单** 可取回完整的历史结果，无需再次调用 GPT。

恢复前必须保证数据库候选和导入版本、源规则文件、菜库、已批准 Action 和内部配置未变化；原始菜单Excel不再作为运行时依赖，文件改名或移走不会影响已入库菜品。不符合快照时要求重新生成，不混用不同版本。新流程还会复用失败周内已完成档口，只继续未完成部分；旧记录按已知旧模板恢复。每次模型输出在校验前写入私有记录，运营 API 不显示原始响应或 Prompt。用量区分本次调用、最终采用输出和历史复用；网络超时也可能已产生费用，请勿盲目重复点击。

需要更新原菜单来源时显式执行以下命令；运行中有菜单会拒绝导入。默认只读预览，`--apply`先备份、事务写入，重复导入不重复加菜/来源，不覆盖人工字段：

```powershell

node tools/Import-StallCatalog.mjs --apply
```

一次六周通常约84次排菜调用（14个需AI档口×6周），加1次独立检验；人工上传、固定出品或没有可行候选的档口不调用排菜AI。局部纠错还会增加请求，实际时间和费用取决于模型，不能按旧版7次调用估算。失败恢复会复用已完成档口，不重新计费生成它们。

质量分由服务端据实际菜单计算，目标为80分：完整供给30、规则合规25、重复轮换20、批准Action执行15、可核验性10。缺位、硬规则和重复真实扣分；未知标签仅降低可核验性，不伪造已核实值。没有排菜Action时该项标记N/A、不扣分，不冒充执行成果。单档最多两次追加纠错，保留真实返回中冲突较少的一版；不保底80、不无限重试。

六周及独立审核完成后显示分数；部分、过期或未审核记录不计算新分。点击“查看评分与冲突详情”查看各维度、实际冲突、AI发现及来源。即使80分以上，有阻断仍不能发布。批准Action卡片展示批准版本、要求、落实/部分落实/未落实、说明及具体周次/日期/菜品位置，不宣称未做对照试验的因果效果。

菜单页默认勾选“启用 AI 排菜员与检验员”，不再显示“模拟排菜测试”入口。已有历史模拟记录仍可读取并明确标识；主动取消 AI 才会生成未经过 GPT 的本地规则草案，不会在 AI 失败时自动降级。页面说明菜品已完成本地入库，排菜直接读取数据库候选，无需再次预处理。

进入六周菜单即显示常驻 **排菜 Action** 面板，无需先生成菜单。面板展示当前可用于下一次AI排菜的要求，以及待审批、已停用、已拒绝、缺少排菜要求或反馈关联的事项和原因；服务及其他非排菜改善单独统计，不混入选菜条件。点击“管理 Action 事项”可前往编辑/审批，保存后返回面板同步更新。界面与服务端使用同一参与判定，读取统一API的当前数据；下方菜单执行记录仍明确为生成时快照，不把后来批准的要求算作旧菜单已经落实。

评分详情将本地冲突与 AI 发现合并为“档口 / 日期 / 餐次 / 冲突 / 核验 / 操作”明细，每页10条，可按档口与级别筛选。可定位的硬冲突提供 **AI 修复**：经已配置模型发起一次请求，仅调整该档口当天该餐次的菜品，之后重新校验整份六周菜单。只有目标冲突减少且没有新增冲突或标签缺口时才接纳；否则保留原菜单，不自动重试。人工菜单、固定出品来源缺失、未知标签以及未定位的 AI 汇总项仍需人工处理，不会用“已解决”隐藏问题。

修复等待只作用于菜单页，切换其他页面可继续操作。接纳修复后旧评分与检验记录失效，Action 标注为上次审核记录；点击“重新 AI 检验”（会另行调用模型）后再保存草案。修复不覆盖已保存菜单、原始生成记录、菜库或审批，并记录实际替换槽位供追溯。

## 转换与工作流接口

接口可按 `DINING_NETWORK` 配置供本机或公司内网可信用户访问，也可通过上述 Cloudflare 演示隧道访问，认证由所选 `none` 或 `basic` 模式决定；浏览器写请求须来自各入口的同源地址。除文件上传外，写请求使用 `Content-Type: application/json`。上传使用 `application/octet-stream` 原始文件字节，`X-File-Name` 为经 `encodeURIComponent` 编码的文件名。

| 接口 | 用途 |
| --- | --- |
| `POST /api/feedback/upload` | 上传旧格式XLSX，自动转换、幂等入库；返回批次、映射与计数 |

| `POST /api/feedback/convert`，`{"import":true}` | 兼容旧的本机固定文件接口；页面日常使用上传入口 |
| `GET /api/imports/:id/download?format=xlsx` | 下载该批次目标格式工作簿；也支持 `csv` |
| `POST /api/feedback/:id/analyze`，`{}` | 单条反馈摘要与回复草稿，不创建行动；相同输入复用分析 |
| `POST /api/feedback/:id/reply`，`{"text":"回复内容"}` | 保存本地回复及历史 |

## CSV 约定

CSV使用UTF-8、逗号分隔、标准CSV引号规则。CSV单批最多10,000行，请求不超过5MB。反馈中心另支持上传原始Forms格式XLSX（10MB），自动转换为新表；其他任意版式Excel不作猜测映射。

### 反馈导入

```csv
content,restaurant,date,channel,type,category,threadId,owner
示例反馈请替换,寻味列车,2026-09-05,手工,建议,口味,,
```

`channel`：手工、口头、微信群、二维码、邮件；`type`：建议、投诉、表扬、询问。按规范化字段内容去重，重导同一行不新增，不覆盖现有处理状态。CSV记录默认未处理及疑似重复待核验。

邮件线程续写目前通过“录入反馈”入口使用相同渠道与线程标识完成；CSV不是邮箱连接器。模板里的示例不是实际反馈。

### POS 导入

页面可下载CSV模板。金额为人民币，时间为北京时间，不含时区后缀。

```csv
transactionId,lineId,time,stall,dishId,dishName,quantity,amount,status,unit
POS01-20260905-001,1,2026-09-05T12:30,寻味列车,,奥尔良鸡腿,2,16,sale,份
POS01-20260905-R01,1,2026-09-05T13:30,寻味列车,,奥尔良鸡腿,-1,-8,refund,份
```

- 唯一键为交易号+明细行号。交易号不是全局唯一时应加终端/门店前缀；退款使用自己的交易号，不覆盖原交易。
- `status`：`sale`、`refund`、`void`。销售数量为正；退款数量为负、金额非正；作废不计。金额最多两位小数。
- `unit`：份、个、斤、100g、位。不同单位不混排行，多件套餐以套餐份计，原规格保留在菜名/价格文字中。
- `dishId`可从菜品资料导出获取。留空时按“档口+完全一致菜名+单位”唯一匹配，多价版本或无法唯一匹配时保持未映射。
- 未映射明细仍计入收入，不进入菜品排行。只含刷卡金额时不能推断菜品销量，交易数不是人数。
- 同键同内容跳过，同键不同内容整批回滚。纠错需冲正记录或后续更正流程，不支持重导覆盖。
- 模板示例不是实际交易，正式导入前必须替换。

### 菜单生成与导出

点击“一次生成全部档口六周菜单”，一次请求覆盖当前菜库中全部17个档口分组、六周周一至周五和所选餐次。无需逐档口操作；缺少可用候选的档口仍保留待补菜位置。所选餐次统一应用于全部分组，实际开餐时间、早餐库归属及固定主食需要现场复核。

默认按周展示所有档口，可筛选某个档口、周次或餐次；这些筛选只影响查看。点击菜名查看辣度、素食性、热量、过敏原、标签依据、来源及配方证据，也可在明细中更换同档口菜品。换菜后整份重新校验，点击“保存整份草案”保存为一个完整版本。已有单档口历史草案继续可读，不会自动补成全部档口。

“导出六周菜单”输出周菜单表，列为：**周次、日期、餐次、档口、周一、周二、周三、周四、周五**。日期为对应周的起止日期，每个工作日单元格仅含菜名及原售价，空槽位标为“待补菜”。导出始终覆盖整份草案，不受当前筛选影响；不导出菜品ID、槽位、种子、状态、规则、原料、营养或来源明细。

纯菜单文件用于阅读、分发或打印，不是内部排菜备份；旧菜单明细CSV导入入口已撤下，调整在页面菜品明细中完成。

## 存储与安全

首次启动生成应用私有数据库`app/data/dining.sqlite`，不纳入Git。备份前停止服务并复制整个`app/data`目录；恢复时保持服务停止，恢复该目录后重启。不要删除数据库来刷新页面，这会丢失人工记录。

原始资料、解析产物、测试截图可能包含个人反馈和身份线索，不应公开上传。界面未展示身份专列，但正文仍可能含签名，不属于完整脱敏。应用直连入口没有登录验证；Cloudflare 演示入口支持无需登录的 `none` 和验证共享账号口令的 `basic` 模式，均不验证公司身份。当前仍没有公司 SSO、角色隔离、加密备份或生产审计，正式部署需另行补齐。

真实邮箱/POS接口、跨档口全局求解、自动营养核算、采购库存及损耗预测尚未接入。AI已接入指定Azure endpoint，仅在用户选择AI流程时发送所需业务文本；源表身份专列不进入反馈分析请求，但正文仍可能含身份线索。上线门槛见项目文档。
