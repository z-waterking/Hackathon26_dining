# 餐叙 · BJW 餐饮运营工作台

本地初版 v0.1，包含反馈中心、六周菜单、菜品资料和消费分析。使用真实资料初始化 SQLite，不需要云账号或 API Key。

项目目标与业务边界见 [项目文档](docs/项目文档.md)，原始笔记保留在 [project.md](project.md)。

## 启动

环境：Node.js 24、npm、PowerShell 7。首次在当前工作区运行：

从 GitHub 克隆后，需通过授权渠道另行取得原始资料，并按原文件名放到项目根目录：`六周菜单.zip`、`新六周菜单.zip`、`第一轮+第二轮纯菜单库.xlsx`、`餐厅排菜规则+示例.xlsx`、`微软BJW园区餐饮反馈(1-147).xlsx`、`新餐厅反馈记录表-from 202607 3.xlsx`。原始资料、反馈截图、解析产物、数据库及环境密钥不随代码提交；未取得资料时，首次数据库初始化和依赖资料的测试不能运行。

```powershell
./tools/Prepare-Materials.ps1
npm --prefix app ci
npm --prefix app run build
npm --prefix app start
```

打开 <http://127.0.0.1:4317>。当前机器的资料已解压、解析，依赖已安装，之后通常只需要 `npm --prefix app start`。

若4317已占用，在同一终端先运行 `$env:PORT = '4318'` 再启动，访问对应端口。服务只绑定本机地址，不面向局域网或互联网。

前端开发：一个终端 `npm --prefix app start`，另一个终端 `npm --prefix app run dev`。Vite将`/api`代理到4317。生产试用只需要单服务启动。

## 数据现状

- 完整解析16份正式工作簿、69张工作表、22,365个非空行、183,410个非空单元格；忽略3个Excel锁文件。
- 初始2,733个档口售卖项，不等于2,733道全局唯一菜。名称、价格或档口不同不擅自合并。
- 保留1,416份配方证据和56个源表公式错误的定位。配方可能有重复版本，成本是原表缓存值，不是重新核算结果。
- 初始195条反馈记录，含月汇总和疑似重复。48个预填渠道空行不入库；问卷前10行隔离为测试/试填待核验；88处同来源序号且正文完全一致的重复已合并。
- 历史跟进文字不等同完成证明，初始没有强行标为已完成的记录。
- 无真实POS明细。默认报表为空，演示交易仅在内存中，不写入真实数据库。

解析目录为本机 [materials/inspection/inventory.json](materials/inspection/inventory.json) 及对应逐表JSON/TXT。数据库初始化只执行一次，重启不会覆盖人工修改。更新源Excel后重新解析也不会覆盖数据库，需要另外制定增量导入策略。

## CSV 约定

使用UTF-8、逗号分隔、标准CSV引号规则。单批最多10,000行，请求不超过5MB。页面支持标准化CSV，不支持直接上传任意版式Excel；已有Excel由资料脚本处理。

### 反馈导入

```csv
content,restaurant,date,channel,type,category,threadId,owner
示例反馈请替换,寻味列车,2026-09-05,手工,建议,口味,,
```

`channel`：手工、口头、微信群、二维码、邮件；`type`：建议、投诉、表扬、询问。按规范化字段内容去重，重导同一行不新增，不覆盖现有处理状态。CSV记录默认未处理及疑似重复待核验。

邮件线程续写目前通过“录入反馈”入口使用相同渠道与线程标识完成；CSV不是邮箱连接器。模板里的示例不是实际反馈。

### POS 导入

页面可下载CSV模板。金额为人民币，时间为北京时间，不含时区后缀。

```csv
transactionId,lineId,time,stall,dishId,dishName,quantity,amount,status,unit
POS01-20260905-001,1,2026-09-05T12:30,寻味列车,,奥尔良鸡腿,2,16,sale,份
POS01-20260905-R01,1,2026-09-05T13:30,寻味列车,,奥尔良鸡腿,-1,-8,refund,份
```

- 唯一键为交易号+明细行号。交易号不是全局唯一时应加终端/门店前缀；退款使用自己的交易号，不覆盖原交易。
- `status`：`sale`、`refund`、`void`。销售数量为正；退款数量为负、金额非正；作废不计。金额最多两位小数。
- `unit`：份、个、斤、100g。不同单位不混排行，多件套餐以套餐份计，原规格保留在菜名/价格文字中。
- `dishId`可从菜品资料导出获取。留空时按“档口+完全一致菜名+单位”唯一匹配，多价版本或无法唯一匹配时保持未映射。
- 未映射明细仍计入收入，不进入菜品排行。只含刷卡金额时不能推断菜品销量，交易数不是人数。
- 同键同内容跳过，同键不同内容整批回滚。纠错需冲正记录或后续更正流程，不支持重导覆盖。
- 模板示例不是实际交易，正式导入前必须替换。

### 菜单生成与导出

点击“一次生成全部档口六周菜单”，一次请求覆盖当前菜库中全部17个档口分组、六周周一至周五和所选餐次。无需逐档口操作；缺少可用候选的档口仍保留待补菜位置。所选餐次统一应用于全部分组，实际开餐时间、早餐库归属及固定主食需要现场复核。

默认按周展示所有档口，可筛选某个档口、周次或餐次；这些筛选只影响查看。点击菜名查看辣度、素食性、热量、过敏原、标签依据、来源及配方证据，也可在明细中更换同档口菜品。换菜后整份重新校验，点击“保存整份草案”保存为一个完整版本。已有单档口历史草案继续可读，不会自动补成全部档口。

“导出六周菜单”输出周菜单表，列为：**周次、日期、餐次、档口、周一、周二、周三、周四、周五**。日期为对应周的起止日期，每个工作日单元格仅含菜名及原售价，空槽位标为“待补菜”。导出始终覆盖整份草案，不受当前筛选影响；不导出菜品ID、槽位、种子、状态、规则、原料、营养或来源明细。

纯菜单文件用于阅读、分发或打印，不是内部排菜备份；旧菜单明细CSV导入入口已撤下，调整在页面菜品明细中完成。

## 存储与安全

首次启动生成应用私有数据库`app/data/dining.sqlite`，不纳入Git。备份前停止服务并复制整个`app/data`目录；恢复时保持服务停止，恢复该目录后重启。不要删除数据库来刷新页面，这会丢失人工记录。

原始资料、解析产物、测试截图可能包含个人反馈和身份线索，不应公开上传。界面未展示身份专列，但正文仍可能含签名，不属于完整脱敏。当前没有SSO、角色隔离、加密备份或生产审计，不能直接开放网络访问。

真实邮箱/POS接口、云端AI、跨档口全局求解、自动营养核算、采购库存及损耗预测尚未接入。上线门槛见项目文档，本地初版验收不等同生产上线。
