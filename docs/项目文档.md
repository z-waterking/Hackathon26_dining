## 1. Goal 与完成定义

交付一个可本地运行、可持久化的餐饮运营工作台，使用现有真实菜库与反馈资料，完成反馈处理、跨反馈改善事项审批、六周菜单编排和 POS 消费分析流程。当前所说的“完成”不代表真实邮箱、POS 供应商 API、企业身份认证已经上线。

- 资料：两个菜单包完成解压，当前17个正式工作簿、72张工作表完成单元格扫描；保留原始资料，不把3个Excel锁文件当业务文件。目标历史表优先读取2.xlsx，3.xlsx副本不重复入库。
- 文档：需求、资料现状、规则冲突、数据模型、实施边界和运行方法有据可查。
- 反馈：旧格式XLSX上传后自动转换、页面展示新表、历史导入、手工录入、四卡仪表板与反馈台账、回复草稿、状态变更、月度汇总和导出可用。
- 改善事项：从全部或指定月份反馈归纳0–6项共性行动，保留原文证据，由运营调整业务要求并审批；相同主题复用已有事项，保留人工决定。
- 菜单：真实菜库检索、标签维护、六周草案、单菜替换、规则检查、保存及导出可用；不能满足的约束明确报出，不伪造合规。
- POS：CSV 导入、重复导入保护、按日期和档口聚合、菜品销售排行可用；没有真实数据时显示空状态，演示数据与真实数据隔离。
- 工程：本地数据库保存后刷新不丢失，核心业务测试和桌面/移动端浏览器检查通过。

原始会议记录见 [project.md](../project.md)。用户最初所述“柳州菜单”按原始记录及所有材料解释为“六周菜单”。

## 2. 业务目标

1. 将二维码问卷、邮件、微信群和口头反馈统一归档、跟进和总结，让处理结果可追溯。
2. 从多条反馈中归纳共同问题，以独立 Action 事项记录证据、执行要求和人工批准结果；不为每条反馈强行建立行动。
3. 从已有档口菜库中编排周一到周五的六周菜单，以历史版本、现场能力及已批准的排菜事项为依据调整。
4. 用 POS 实际交易评估消费趋势、档口收入、菜品销量和客流，为后续备餐与减少浪费提供证据。

远期目标是适量备餐、减少浪费。采购、供应商订单、入库、领料及损耗管理不是本次初版的交付承诺。

### 数据问题

- 菜名存在近义、错字、别名和相同名称不同售价，例如菠萝咕咾肉/菠萝古老肉、同名蔬菜价格差异；不得凭文字相似自动合并。
- 菜库按多组横向“名称+价格”排列，不能把每行当一条菜；套餐、称重、按个及按斤计价必须保留原单位。
- 规则示例和纯菜库不总是一致：蒸心食意的示例菜有的落在纯库百变厨房列。不能自动跨档口挪用。
- 成本预估存在 `#N/A`、`#REF!`；错误值不能转换成0元成本。
- 反馈表日期混用 Excel 日期序列、英文日期、姓名加时间、整月文本；不明确到日的记录应保持月级精度。
- 7月反馈部分“反馈类别”和“问题分类”填反；微信群多问题月汇总不能与单条问卷混作同口径计数。
- 问卷和跟进表有重复的来源序号，但也有无序号邮件。仅凭序号或相似主题不足以安全合并，须核对正文。
- 有跟进内容不代表已完成，没有完成时间不能编造完成时长。初始状态采用“有有效跟进则跟进中，否则未处理”，历史状态待人工核验。
- 原始材料含邮箱、Alias、签名等个人信息。初版不展示身份专列；业务原文仍可能含个人信息，仅供本机授权使用，不得公开部署。
- 当前无 POS 交易文件、API 规范、刷卡明细样例及园区到访数据。“就餐约80%”仅是会议经验，不是测量值。

## 4. 用户与工作流程

目标角色：餐厅运营处理反馈，厨师长管理菜品与审核菜单，管理者查看报表，管理员管理导入与字典。初版是本地可信操作人员使用，不声称具备企业级多角色权限。

### 4.1 反馈中心

流程：上传旧问卷/录入 → 新表与来源核对 → 单条反馈处理/回复 → 跨反馈聚合事项 → 人工审批 → 菜单或运营改善。反馈状态仍为未处理、跟进中、已完成，允许重新打开，记录每次变更和处理备注。

进入反馈中心即显示首页，不再设置“处理工作区”或“反馈台账”页签。顶部 AI 横幅说明根据多条反馈自动归纳改善事项，并可跳转独立“Action 事项”；主体仅保留规整排列的四卡仪表板和反馈台账。四个仪表卡分别展示按类型分类的反馈趋势、反馈类型分布、外置词云、处理概览；月份为空时统计全部真实月份。图表将“投诉”与历史“批评”统一展示为“批评”，台账原始分类不改写。完整反馈台账和转换后的十列表仍保留，筛选、分页、长正文展开、进入单条反馈处理/回复与下载继续可用。首页不放聚合生成区，跨反馈归纳、业务要求编辑和审批统一在 Action 模块完成。

用户只需上传任意文件名的旧 Forms `.xlsx`，无需上传目标模板。原件进入独立上传批次目录，转换产物为按月XLSX、CSV及带溯源的JSON；新表直接在系统展示。重复记录不新增、不覆盖人工状态与回复，原文和源文件保持可追溯。文件/ZIP结构、解压大小及XML实体声明在解析前检查，不猜测任意未知版式。

基础字段：来源ID、渠道、原始餐厅、标准档口（可空）、反馈日期/精度、类型、问题分类、正文、负责人、状态、跟进历史、来源文件/表/行。

邮件同线程续写是目标需求。初版提供手工线程标识，同线程追加处理记录而不是创建第二条；真实邮件连接器需等待邮箱权限与线程字段。微信群及口头支持手工录入，不做未经授权的抓取。

单条反馈的 AI 分析仅归纳摘要并起草回复，回复由运营保存到本地，不自动发送邮件，也不产生逐条Action。首页词云直接展示当前月份范围的餐饮实词/短语，字体大小按提及该词的真实单条反馈数计算，同条重复提及不重复计数；月级汇总、已知试填和演示反馈不计入。首页统计及词频仅在本地读取计算，不调用 AI、不写入报告或审计记录。AI月报仍为另一个按需调用入口，需区分反馈观点和已核实事实。只有明确完成时间的数据才能计算处理时长。

### 4.2 聚合 Action 事项

默认以全部月份真实单条反馈为一次输入，也可选月份。页面保留真实AI生成、月份/状态筛选及事项卡片。卡片按排菜优化、服务改善、运营提升区分配色，展示优先级、措施摘要、原文依据、关联数、版本和审批状态；桌面三列、平板两列、手机单列，点击“查看与审批”在详情中读完整正文和证据、编辑并审批。从跨反馈共同关注中提炼0–6个可执行事项，以“核验、措施、验收”描述；一个事项可对应多条反馈，不要求每条均有事项。模型选择完整原文的段落ID，由服务端回填逐字证据，未知或跨记录引用拒绝入库。超过1000条或150000字符时明确提示缩小范围，不截断后冒称完整分析。

运营可编辑标题、说明、目标档口、优先级、排菜调整要求及启用状态，并通过审批理由批准或拒绝。新事项默认待审批；复用同主题事项只补充依据，不覆盖人工内容、修订号或已作出的审批。排菜事项需有具体菜单要求；服务、清洁、排队等事项保持排菜要求为空。只有已批准且启用的真实排菜事项影响正式菜单。

业务角色Prompt与AI规则通过左下角“Prompt 与规则”和专用`/api/prompt-config`查看/编辑，版本与来源指纹保护并发保存；`/api/settings`旧入口仍404。其余业务API不回传原始Prompt、模型输入或内部配置；运行留痕仍只展示业务快照与证据。新配置只用于下一次，当前运行保留启动快照，源规则原文不覆盖。本地硬编码校验只读列明，任意文本编辑不改变程序阈值。

聚合结果按范围、完整来源和实际 Prompt 指纹保存，页面每次显式点击生成以force=true调用真实AI；打开页面只读取结果。等待AI期间反馈、已有事项或内部分析设置变化则拒绝保存过时结果；独立 Prompt 配置更新不混入当前请求，下一次按新文本重新分析。失败保留原有结果、不伪造替代事项。历次聚合与业务修改写入本地审计。接口见README中的`/api/actions/summary`与`/api/actions/summarize`。

Action页面不再提供“加载示例”或“示例事项”切换。既有12条示例反馈、4个聚合事项保留为历史隔离数据，不删除、不自动转真实、不参与本次AI输入。底层模拟接口和对应回归测试保留，正式AI流程仅使用真实记录。

通用校验：同日期/餐次/档口内菜不重复；从所属档口菜库选；已停用菜不可选；保存单菜替换后重新检查；从周一开始六周、每周五天。寻味列车、五味坊、一锅烟火、蒸心食意午晚及近两天同餐次避重；南粉仅午晚避重；饺好运午晚至少50%不同。合法寻味/五味共享不会误报跨档重复。

“至少30%替换”分母尚未确认。全档口草案对比上一个已保存的全档口草案，历史单档口草案对比同档口版本，展示槽位变化率，不将其冒充“新品率”；档口、周次、餐次或槽位不具有可比性时显示不可计算。菜库不足则保留缺位和告警，不编造菜品。

菜单流程：本地规则同步 → 已批准事项快照 → GPT逐周直接选择最终槽位（六次） → 本地校验 → 独立GPT检验 → 人工调整/重新检验 → 保存 → 导出。`app/server/prompts/menu-planner.md`与当前文件规则、批准事项组成system级instructions；每周完整有效菜库和前序菜单为输入。只有显式关闭AI才生成本地规则草案，模拟路径单独保留。正式菜单不会自动发布；源规则/标签不足与人工菜单缺口保留，不把生成成功冒充合规。

2026-09-06确认：生成单位为**全部档口的一整份六周菜单**，不再要求逐档口生成。按当前菜库的全部档口分组、六周工作日及所选餐次批量编排，保存成一个版本；无可用菜的档口保持空槽并告警。查看按周、餐次展示所有档口，可筛选到单档口；点菜品查看详细标签、来源与配方证据，换菜仍限制在原档口。旧单档口草案可读且不自动扩容。

导出为纯菜单CSV：周次、日期、餐次、档口、周一至周五，单元格只含菜名及价格。导出包含草案的全部档口、六周和所选餐次，不随页面筛选缩小范围；不包含ID、槽位、状态、来源、营养、配方或规则明细。详细信息只在应用查看，旧明细CSV回导入口撤下。

全量校验汇集每个档口的问题，并检查同日同餐次跨档口同名菜，标出需要按共享例外复核的项目；这不是已经解决所有跨档口冲突的全局优化器。生成范围目前是菜库分组而非已确认的实际开餐表，实际餐次范围仍需现场复核。

菜品标签：主料、工艺、辣度、素食性均可人工维护。每100g热量、过敏原及配料必须有可靠来源，未核实为未知；不因菜名不含花生而标“无花生”。翻译可复用原表，待专业复核，缺失不杜撰。

### 4.4 POS 分析

一期以 CSV 明细为入口，供应商 API 后续替换导入适配层。建议字段：交易号、明细行号、交易时间、档口、菜品ID、菜品名称、数量、实收金额、状态。称重商品应另有重量与单位，不能把100g份数和整份混排行。

- 净收入：有效销售金额减退款金额；作废不计。退款以独立负金额、负数量记录，来源需提供唯一行号。
- 交易笔数：成功销售的交易号去重，不等于人数；平均每笔金额需标清分母。
- 菜品销量榜：仅统计已映射菜品、可比单位的净数量。只有档口刷卡金额时不能展示单菜销量结论。
- 档口排行、日趋势、周/月/季度过滤可用；未映射菜品单独统计并显示覆盖率。
- 无卡标识时不计算独立就餐人数；无园区到访数据时不计算转化率。
- 演示模式只在内存生成模拟交易，不写入真实交易表，不与真实报表混算。

## 5. 技术方案

本地单体 Web 应用：Node.js 24、Fastify、SQLite、React + Vite。数据库位于应用私有数据目录，服务仅绑定 `127.0.0.1`；静态服务器不暴露原始反馈文件或解析目录。图表使用Recharts、图标使用Lucide、中文字体为本地Noto Sans SC。本地转换、台账、统计及模拟排菜不依赖云服务，用户主动选择AI回复、聚合、月报和排菜/检验时通过服务端调用Azure Responses API。

逻辑实体：反馈、回复/处理事件、聚合改善事项及原文证据、菜品售卖项、配方证据、菜单草案/槽位、角色运行留痕、POS明细及来源清单。物理表包括`feedback`、`dishes`、`plans`、`transactions`、`meta`、`actions`、`settings`、`menuRuns`、`imports`、`aiUsage`、`audit`，以稳定ID及JSON存储记录；`settings`为内部配置，不提供运营读取入口。跟进和菜单槽位作为子记录保存，不声称已完成生产级规范化数仓。SQL参数化，导入、聚合保存及审批使用事务，非法输入明确报错。

AI月预算150 USD为本地配置参考，未确认单价时只记录token用量；配置实际单价后估算并阻止超出已记录预算的新调用。该机制不构成Azure硬账单限制，其他应用及进行中请求仍以云端账单为准。密钥仅存服务端环境配置，不纳入Git或返回给浏览器。启动命令、备份方法及部署限制见README。

开发顺序：资料解析 → 导入与测试 → 三模块API → 工作台界面 → 回归测试 → 本地运行交付。

## 6. 初版之后的上线门槛

真实部署前必须确认 SSO/角色权限、原文访问范围、日志脱敏、保留期限、备份恢复、TLS、邮件权限、供应商接口限流/增量/退款口径、食品标签审核流程。缺失的营养库、配方标准及库存数据应补录后再做自动营养核算和采购预测。

待业务确认：五味坊共享例外、30%新品口径、两天避重是否跨周、量味厨房位置与计价单位、归属疑似错列菜、一期实际开餐档口、邮件自动合并策略。上述问题不阻塞本地初版，但阻塞无人工复核的生产排菜。
