# 2026-09-09 本地规则驱动的真实 GPT 六周菜单

## 目标与原有方式

- 用户要求明确排菜规则和 Prompt 来源，将本地文件规则作为系统约束，只用已批准改善事项微调，并真实调用 GPT 生成具体六周菜单。
- 原来的真实 AI 流程主要输出菜品偏好、降低优先级或禁用策略，具体槽位仍由本地规则引擎选择。本轮正式流程改为 `gpt-direct`：GPT 直接决定每个槽位的菜品，服务端负责结构、引用和规则核验，不再用随机菜单代替模型结果。
- 模拟测试与显式关闭 AI 的本地规则草案仍保留，必须明确区分来源，不作为真实 GPT 生成结果。

## 本地规则与系统指令

- 规则来源为仓库根目录 `餐厅排菜规则+示例.xlsx`。`app/server/menu-source-rules.mjs` 读取排菜规则工作表，按合并单元格主格去重，当前源文件整理出 16 条规则、4 条单独的固定主食记录、4 条宽窄巷子固定出品来源。每条保留文件、工作表、行号、单元格、餐次及源文件 SHA-256。
- 固定主食按寻味列车／一锅烟火的午餐、晚餐分别记录。附加主食不塞入热菜槽位，也不能因主食固定而把整个档口的热菜误标为固定出品。要求人工提供的主食保留人工核验缺口。
- 规则同步在完成文件读取、解析后原子更新本地元数据，并写入 `menu.rules_synced` 审计。文件缺失或解析失败不会清空上一版规则；源文件警告和版本指纹随运行保留。
- 排菜系统模板位于 `app/server/prompts/menu-planner.md`。`directPrompt()` 将 Markdown 模板、本地来源规则，以及已批准运营调整组合成服务端指令；运行快照记录实际组合与指纹。运营仍只编辑 Action，不直接查看或编辑原始 Prompt。
- 约束顺序为真实、启用且同档口的菜库候选与槽位限制 → 本地源规则 → 已批准事项的允许范围内微调。明确源硬规则不能被 Action 覆盖；源规则缺失、冲突和未知标签必须如实记录，不虚构已核验事实。

## 直接选菜与独立检验

- 正式排菜按 6 个周次依次真实请求 GPT，每次编排该周全部工作日、所选餐次与所有档口；传入之前已选周次用于跨周轮换。输入包含完整有效候选菜库，不抽样或截断；超出输入限制时直接报错。
- GPT 返回各档口按日期、餐次、槽位顺序排列的菜品索引，服务端映射回真实菜品 ID。数量错误、档口遗漏／重复、候选外引用、跨档口引用、人工上传档口被代填等结果会被拒绝，不用本地算法补齐。若存在有效候选却返回整份空表，也不会将其作为菜单成功返回。
- 本地规则要求人工上传的档口继续保留待补位置。没有专属规则的档口可按通用槽位生成候选草案并说明假设；未知辣度、素食性、主料、工艺、营养、成本、库存或过敏原不能被说成已核验，也不应仅因标签未知就把整个档口留空。
- 六周合并后执行本地校验，再由独立 GPT 检验员读取实际完整六周槽位、真实菜库、源规则、已批准事项、本地校验与 Action 位置记录进行复核。检验员不能只相信排菜员摘要。
- 本地硬错误会强制阻止检验通过；已批准事项未全部落实时要求复核。检验结果始终只是辅助建议，保留 `requiresHumanApproval`，不等于运营批准、保存或菜单发布。

## 已批准 Action 与可追溯边界

- 只有关联反馈、处于 `approved`、明确启用且有非空排菜调整要求的真实 Action 参与正式排菜；未批准、已拒绝、停用、纯服务事项及示例事项不参与正式排菜。服务／流程改善继续由运营跟进，不强行转成换菜。
- 系统指令中的运营调整包含事项 ID、标题、指定档口、排菜要求、优先级及修订号。跨范围调整或与源规则冲突时必须说明，不能自行修改审批记录。
- 每周返回 Action 的 `applied`／`partial`／`not_applied` 说明及真实菜单位置。服务端检查证据位置确实存在、有实际菜品且未超出批准档口；没有位置证据不能声称已全部落实。缺失周次说明按未落实处理。
- 页面中的本次关联槽位、菜品及周次位置是执行记录，不是与“无 Action 菜单”相比的因果提升。直接生成模式不显示虚构基线槽位或变化数量。
- 菜库、标签、源规则文件、内部配置、系统模板或已批准事项版本变化，会使正在生成或既有检验记录失效，要求重新生成／复核；手工改菜后也不能继续沿用原来的检验通过结论。

## 页面交互

- 六周菜单默认启用 AI 排菜员与检验员，起始日期默认为下一个周一。AI 未配置时明确禁用真实生成并说明原因，不静默降级；用户显式关闭 AI 后才能生成标明“未调用 GPT”的本地规则草案。
- 生成使用菜单页面内的等待状态，不显示全局遮罩。请求在后台继续，用户可以导航到反馈中心等页面；本页防重复提交和冲突编辑，完成后不强制切回或抢焦点。
- 失败明确报错，已有草案保持不变，不插入示例或替代菜单。生成完成只展示待审核草案，仍由用户点击“保存整份草案”。
- 页面展示规则文件与版本指纹、规则数、排菜员／检验员模型、源规则警告、人工核验和未解决要求，避免把生成成功误当作可以直接发布。
