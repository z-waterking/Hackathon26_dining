# 2026-09-08 独立 Action 模块与运营说明更新

## 业务流程

- 按用户要求，将 Action 从单条反馈分析中分离。单反馈AI仅生成摘要与回复草稿；全量或指定月份反馈统一聚合为0–6个共性事项，不强求每条反馈都有Action。
- 每项保留多反馈ID和逐字原文证据，由服务端验证其属于本次范围。相同主题重算复用事项，补充依据时保留已有人工修改和审批。
- 主导航设独立“Action 事项”。运营调整标题、说明、目标档口、优先级、排菜调整要求、启用状态和审批理由，集中批准或拒绝。服务/清洁/排队等事项不填写排菜要求；只有已批准且启用的排菜事项进入正式规划。

## 界面与内部配置边界

- 反馈中心提供总览与参考布局的三栏处理工作区：反馈队列、原文/处理/回复、跨反馈热点/待审事项。完整台账与上传转换新表保留。
- 撤下原运营Prompt编辑界面，角色配置由应用内部维护。`GET /api/settings`及`PUT /api/settings`停用并返回404。
- API不回传`rawPrompt`、角色Prompt、原始角色输入或内部配置。菜单运行留痕展示业务范围、规则和Action快照、决策、检验及影响证据；运营通过改善要求影响规划，无需接触模型消息。

## 演示流程

- 示例数据为12条反馈、4个聚合事项，每项关联3条反馈原文，均明确标记demo并与真实范围隔离。幂等加载不重置人工修改或审批。
- “加载示例 → 人工批准 → 模拟排菜/重新模拟检验”全部使用本地逻辑，不调用Azure。AI聚合和正式AI排菜是另外的显式入口，会使用API。
- 模拟器只执行内置偏好、减少、禁用映射。编辑示例指令、档口或优先级会使原映射失效，需显示未落实/人工验证，不能声称理解了任意自然语言调整。服务示例不改变菜品。

## 集成与历史兼容核验

- 本地既有1条旧逐条待审批Action保留原记录，不删除或修改审批；新模块、反馈关联区和排菜要求集合不再消费旧单反馈结构。真实范围通过整体汇总生成新的改善事项。
- 编辑业务要求时同步Action分类，服务事项填写排菜要求后转为排菜事项，清空后不进入菜单。示例检验在路由入口核对显式demo模式，不能被服务端恢复字段绕过。
