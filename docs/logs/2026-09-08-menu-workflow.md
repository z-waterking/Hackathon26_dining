# 2026-09-08：六周排菜员、检验员与行动影响追踪

## 修改内容

- 新增 `app/server/menu-workflow.mjs`，完整流程为：锁定运营配置、原始排菜规则和批准行动快照 → AI 排菜员生成菜库选择策略 → 本地规则引擎一次生成全部档口的六周工作日菜单 → 独立 AI 检验员检查实际菜单 → 留作人工审核草案。
- 排菜员使用主服务统一的 Azure Responses 客户端，不管理或保存 API 密钥。角色分为 `planner`、`inspector`，两次调用分别记录模型、请求 ID 和 usage。
- 从 `meta.rules` 读取原表规则，保留文件、工作表和行号，为每条规则分配稳定引用 ID。规则适用范围包含同表续行继承、多档口组合名称和“铁锅炖 → 一锅烟火”别名，不允许引用别档口规则改变本档口。
- 只有 `status === 'approved' && enabled === true` 且 `menuInstruction` 非空的行动进入排菜提示。原始反馈不再直接对菜品降权；旧 `feedback` 参数保留兼容性，但不影响排菜。
- 模型只能输出真实候选菜的 `prefer`、`avoid`、`exclude` 策略。偏好/回避实际改变评分，禁用实际移除候选。每个策略必须引用本轮输入内的行动或源规则，行动必须匹配批准的目标档口；未知 ID、重复策略、越界引用直接拒绝并记录失败。
- 每项批准行动记录菜库策略、未落实原因、无行动基线与实际选用次数、变化槽位数。基线保留仅由源规则产生的策略，排除行动策略。没有模型策略的行动也必须显示为未落实。计数是整轮有/无行动策略的对比，不宣称能隔离多行动间的因果影响。
- 检验员收到真实六周全部槽位、实际菜品与标签、源规则、本地校验汇总和行动影响结果。未知标签不补造；本地硬规则错误或未全部落实的行动会强制 `revise`，模型不能覆盖这些检查。
- AI 结果不会产生“已批准”或“已发布”状态；`needs_review` 仍需运营人工审核，存在错误或未落实行动时为 `blocked`。

## 运营调试与留痕设计

运营配置沿用版本化的 `plannerPrompt`、`inspectorPrompt`、`operatorNotes`；行动可单独修改 `targetStall`、`menuInstruction`、优先级及启用状态。每轮 `menuRuns` 保存：

- `snapshots.settings/rules/actions/dishes`：本轮使用的配置、规则、批准行动和菜库。
- `snapshots.prompts`：实际传给两个角色的完整提示词，包含固定的 JSON 契约和约束。
- `plannerInput/inspectorInput`：当次模型业务输入。
- `planner/workflow/plan`：策略、检验结论、行动影响和最终菜单。
- `stage/status/createdAt/completedAt`：运行阶段、结论和时间；失败保留 `failedStage/error`，不产生可信的通过状态。

菜单指纹覆盖完整日期、档口、餐次、槽位和菜品 ID。人工换菜后重新检查或保存会从服务器恢复可信检验记录，比对指纹并标记 `stale`；客户端自报的“pass/approved”不能覆盖服务器结果。重新使用策略已禁用的菜品会显示 `POLICY_EXCLUDED`。

行动、源规则、菜库标签或排菜相关提示词发生变化，也会使原检验过期；后台调用期间发生的变化在响应前即可发现。反馈回复提示词单独变化不会使菜单过期。仅手动换菜或修改检验提示词可以再次调用检验员，不重复付费调用排菜员；行动、源规则、排菜提示词、运营备注或菜单日期/餐次配置变更需重新生成。再次检验另建运行记录，以 `parentRunId` / `plannerRunId` 追溯原排菜过程。

## 成本与数据规模

排菜员最多提供 600 个分层候选，覆盖档口、单位和价格，优先包含行动明确提到的菜名；最多返回 80 个策略。候选采样不代表其余菜品不存在，本地引擎仍使用全部菜库。超过 200 项已启用排菜行动需先合并或停用。

检验输入对菜品字段和槽位使用带字段名的紧凑数组，保留全部实际菜单，不以采样代替全量检查。初次生成正常需要 2 次模型调用，再检验需要 1 次；不做自动重试或反复修订循环。每次调用受主客户端配置的输出 token 上限约束。

- 使用真实导入菜库做模拟 AI 烟雾测试：2,733 道菜、17 个档口、16 条源规则，一轮完整双餐次生成 4,380 个槽位。本地生成约 2–3 秒；排菜输入约 118 KB 字符，检验输入由约 438 KB 压缩至约 213 KB 字符。
