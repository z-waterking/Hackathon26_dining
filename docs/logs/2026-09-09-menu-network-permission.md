# 2026-09-09 六周生成首周连接失败

## 证据与原因

- 用户报告一次生成六周仍有问题。只读检查最新三条menuRuns：MR-5db4db60-ed03-49b3-8894-c5e78bbed3ad、MR-af8726ab-c989-42dc-a54c-55544916baa2、MR-c712fe44-f793-4ab5-a6db-3c9c5d971d83。均在第1周、约100ms内失败，plannerBatches为空。
- 对应aiUsage均为`errorCode=EACCES`，没有上游HTTP状态或模型结果。上一次重启使用受限工具环境，驻留Node进程继承了出站限制；此前独立获准联网的联调进程成功，不能证明当时网页后台也能联网。
- 前端没有额外短超时，导航隐藏而非卸载菜单页，失败会保留旧草案并停止动画。本次不是六周输入过大、Azure模型不存在或页面切换丢失状态。OpenAI Docs错误文档用于区分连接失败、HTTP认证错误与超时；没有改模型或密钥。

## 修复

- ai.mjs区分底层EACCES/EPERM，提示本机出站权限阻止、在获准联网终端重启后端，避免让用户重复刷新/换Key。仍只记录安全机器码，不回传上游原文，不自动重试付费请求。
- index.mjs增加显式`--verify-ai`，在同一服务进程中以无业务数据的小请求验证真实GPT。先绑定端口，避免重复启动时浪费诊断token；诊断失败关闭服务。默认启动不会主动调用模型。
- Start-Dining.ps1增加`-VerifyAi`并说明会产生一次小型API用量。README记录启动与排查方法，无需关闭安全软件或TLS验证。
- 先前停止进程命令未成功，经端口核实后通过原执行会话Ctrl+C真正停止受限进程。随后经授权用`npm start -- --verify-ai`启动新驻留后端，端口仍4317，LAN配置不变。

- 新驻留服务真实诊断成功：gpt-5.6-sol，input 91 / output 15 tokens。另一次端口仍占用时的诊断也产生相同用量，随后修正为先占端口再诊断；共两次小请求，不伪报只调用一次。未重跑六周生成，不修改反馈、Action、菜库或草案，仅新增诊断用量记录。
